\usection{Implementación del lenguaje y su entorno}

Antes de iniciar con la materialización de este diseño arquitectónico, fue necesario establecer un entorno de desarrollo basado en tecnologías web estándar, garantizando el cumplimiento del requisito de ejecución nativa en el navegador para facilitar el acceso desde distintos entornos. Se seleccionó TypeScript como lenguaje principal para la programación del motor de ejecución y la interfaz del editor, utilizando Visual Studio Code y GitHub para el control de versiones. Para el desarrollo de la web, se optó por utilizar React debido a su capacidad de reutilización de componentes y soporte para el desarrollo de interfaces dinámicas. Asimismo, para la renderización del grafo de flujos de datos se empleó la librería de React Flow, que proporciona una base sólida para la construcción de editores visuales de nodos y conexiones, con suficiente capacidad de customización para aplicar los estilos propios definidos en el diseño visual del lenguaje.

Siguiendo la metodología incremental seleccionada, el desarrollo se dividió en fases iterativas. A continuación, se detallan las actividades, decisiones técnicas y resultados obtenidos en el primer incremento.

\usubsection{Primer incremento}

El objetivo primordial de este primer incremento fue establecer las bases de la herramienta, centrándose en dos componentes críticos: la interfaz gráfica para la construcción de programas (editor) y el núcleo de procesamiento (motor de ejecución). En esta etapa, el alcance se limitó a la ejecución en un solo dispositivo (el navegador web), postergando la distribución de procesos para siguientes iteraciones.

\usubsubsection{Desarrollo del editor visual}

Se procedió a la implementación de la interfaz de usuario que permite la programación visual. De acuerdo con lo establecido en el diseño preliminar, el énfasis de esta primera versión se colocó en la funcionalidad operativa más que en la estética final. Las principales tareas realizadas fueron:

\begin{itemize}
    \item \textbf{Lienzo de trabajo:} Se desarrolló un entorno de “arrastrar y soltar” (\emph{drag and drop}) que permite a los usuarios seleccionar nodos desde un panel lateral y depositarlos en un área de trabajo infinita.
    \item \textbf{Gestión de conexiones:} Se implementó la lógica para trazar “arcos” o cables entre los puertos de salida de un nodo y los puertos de entrada de otro, estableciendo así el grafo de flujo de datos.
    \item \textbf{Representación visual de nodos:} Se utilizaron íconos temporales para los nodos, priorizando la correcta identificación de los tipos de puertos (entradas y salidas) sobre el diseño gráfico definitivo del lenguaje.
\end{itemize}

\usubsubsection{Desarrollo del motor de ejecución}

Para procesar los grafos creados en el editor, se construyó un motor de ejecución basado en un intérprete, lo que permitió evitar la compilación para facilitar la depuración y la ejecución inmediata en entornos web.

El motor se diseñó bajo el principio de activación por disponibilidad de datos. A diferencia de la ejecución secuencial tradicional, se implementó un bucle de eventos (event loop) que gestiona el ciclo de vida de los nodos a través de las unidades lógicas definidas en la fase de diseño. Este diseño permitió validar que múltiples ramas del grafo pudieran ejecutarse lógicamente en paralelo sin bloquear el hilo principal del navegador.

\usubsubsection{Refinamiento del catálogo de nodos}

Tras realizar las primeras pruebas de integración entre el editor y el motor, se identificaron oportunidades de mejora en la especificación original de los nodos, lo que llevó a realizar ajustes técnicos respecto al diseño inicial:

\begin{itemize}
    \item \textbf{Especialización de constantes:} Se eliminó el nodo genérico de “Constante” a favor de una tipificación más estricta para reducir errores en tiempo de ejecución. Se implementaron nodos específicos: Constante numérica, Constante lógica y Constante de texto.
    \item \textbf{Expansión de operaciones matemáticos:} Para aumentar la capacidad expresiva del lenguaje en el ámbito aritmético, se agregaron los nodos de Módulo (residuo de la división), Piso (redondeo hacia abajo), Techo (redondeo hacia arriba) y Redondear.
    \item \textbf{Generación de datos:} Se introdujo el nodo “Generar pulsos”, el cual permite emitir valores enteros secuenciales entre un inicio y un fin con un paso definido, fundamental para probar el comportamiento de flujos continuos en el motor, como pudiera ocurrir en un sistema de IoT, por ejemplo.
\end{itemize}

\usubsubsection{Exportación e importación de programas.}

Para permitir el almacenamiento y la transferencia de los proyectos, se implementó un módulo de serialización y deserialización de grafos basado en un formato de texto estructurado y versionado. Este esquema de datos almacena de forma organizada la versión del documento, el nombre del programa, la configuración exacta de los nodos con sus interconexiones, y los parámetros espaciales del lienzo. Durante el proceso de exportación, el sistema extrae el estado actual del entorno y ejecuta una rutina de limpieza para depurar propiedades transitorias o exclusivas de la sesión activa. Esto garantiza que el archivo resultante sea completamente portable. Finalmente, la información validada se empaqueta y se descarga como un archivo local utilizando las capacidades nativas del navegador web.

Por otro lado, durante el proceso de importación, el sistema lee el archivo suministrado por el usuario y realiza un análisis de su estructura interna. En esta fase, se valida de forma estricta la compatibilidad del esquema para asegurar que la versión del documento coincida con la soportada por el motor. Si la validación es exitosa, la rutina de deserialización normaliza los componentes, resuelve posibles conexiones huérfanas y actualiza el estado global del editor. Esto permite reconstruir el flujo de datos visual y restaurar la perspectiva espacial del lienzo tal como fue guardada. En caso de detectar un archivo corrupto o incompatible, el proceso se interrumpe inmediatamente y se notifica al usuario.

\usubsubsection{Implementación de la retroalimentación visual y manejo de errores}

Tomando como base la máquina de estados finitos definida en la arquitectura del motor de ejecución, se implementó un mecanismo en la interfaz de usuario para reflejar el ciclo de vida de cada nodo en tiempo real. Un controlador intermedio intercepta los eventos de estado emitidos por el motor y traduce las transiciones lógicas en actualizaciones dinámicas de estilo sobre los componentes del lienzo.

La materialización gráfica de este comportamiento se configuró mediante contornos coloreados y elementos superpuestos:
\begin{itemize}
    \item \textbf{Esperando (\textit{Waiting}):} Al iniciar el flujo del programa, o mientras aguarda la llegada de todos los datos necesarios en sus puertos de entrada, el componente asume un estado visual caracterizado por un contorno de color gris.
    \item \textbf{Procesamiento activo (\textit{Running}):} Durante la ejecución de su lógica interna, el nodo adquiere un contorno azul e incorpora un indicador de carga animado en su estructura.
    \item \textbf{Ejecución exitosa (\textit{Finished}):} Al concluir su operación y emitir los datos, el componente transiciona hacia un contorno verde de confirmación.
    \item \textbf{Excepciones (\textit{Error}):} Se integró la captura de fallos en tiempo de ejecución. Si un nodo intercepta una anomalía (como incompatibilidad de tipos o datos faltantes), su contorno se torna rojo y despliega un cuadro de texto emergente (\textit{tooltip}) que expone el mensaje exacto del fallo para facilitar el proceso de depuración visual.
\end{itemize}

\usubsubsection{Sistema de tipado y validación de conexiones}

Para garantizar la coherencia de los datos y prevenir errores de ejecución, se implementó un mecanismo de validación de tipos en tiempo real. Cada puerto de los componentes posee una categoría de información específica (como numérico, texto o lógico) que determina su compatibilidad. El sistema evalúa estas reglas continuamente, bloqueando de forma activa cualquier intento de enlazar nodos con tipos de datos incompatibles y emitiendo mensajes descriptivos al usuario.

A nivel de interfaz, este mecanismo rige la representación visual para reducir la carga cognitiva del estudiante. Cada tipo de dato cuenta con una forma geométrica única en los puntos de conexión. Además, el entorno proporciona retroalimentación predictiva: al arrastrar una nueva conexión, el sistema resalta automáticamente los puertos de destino válidos y despliega alertas visuales (\textit{tooltips}) si se intenta forzar un enlace incorrecto, guiando al alumno en la construcción adecuada de su algoritmo.

Como resultado de este incremento, se obtuvo una versión funcional del lenguaje capaz de ejecutar algoritmos matemáticos y lógicos dentro del navegador. Aunque la interfaz visual era preliminar, el motor demostró capacidad para manejar la concurrencia local y la gestión de memoria de los tokens de datos, validando la arquitectura base antes de proceder con la implementación de la comunicación distribuida. En la figura \ref{fig:editor-incr1} se muestra la interfaz del editor en esta etapa, evidenciando la paleta de nodos, el área de diseño del programa y el área de consola para la salida de datos.

Al finalizar las labores de desarrollo correspondientes al primer incremento, se ejecutaron diversas pruebas de validación funcional. Se construyeron programas de prueba integrando los distintos nodos de procesamiento y control implementados hasta el momento. Los resultados de estas pruebas fueron satisfactorios, demostrando que el motor de ejecución procesaba correctamente los flujos de datos lineales y ramificados.

No obstante, como parte de la evaluación pedagógica de la herramienta, se intentó modelar algoritmos clásicos que son fundamentales en el aprendizaje tradicional de la programación, tales como el cálculo del factorial de un número y la generación de la sucesión de Fibonacci. Durante este proceso, se evidenció rápidamente una limitación importante en esta primera versión del lenguaje: la ausencia de soporte para la recursividad. Este hallazgo determinó la necesidad de plantear una solución arquitectónica en los siguientes incrementos para soportar estructuras cíclicas recursivas, garantizando así que el lenguaje no solo sea funcional, sino que posea el nivel de expresividad requerido para la enseñanza integral del pensamiento computacional.

\usubsection{Segundo incremento}

El objetivo central de este segundo incremento fue expandir las capacidades del motor de ejecución, evolucionando de un intérprete local a un sistema distribuido capaz de orquestar procesos en múltiples dispositivos. Se abordó la integración de hardware externo (tarjetas micro:bit) y la ejecución paralela en computadoras remotas, lo que requirió la implementación de protocolos de comunicación robustos para garantizar la consistencia del flujo de datos.

\usubsubsection{Protocolo de distribución a micro:bit}

Para habilitar la ejecución de lógica en el hardware educativo, se diseñó e implementó un protocolo apodado \emph{Micro:bit Dataflow Protocol 1.0} (DFP1). Este protocolo permite desplegar subflujos de lógica compilada directamente en el dispositivo, reduciendo la latencia y la dependencia de la conexión constante, delegando la ejecución del subflujo a la tarjeta.

Se estableció un canal de comunicación híbrido que soporta tanto USB Serial (Web Serial en navegadores) como BLE UART (Web Bluetooth en navegadores), que son los principales canales de comunicación remota con los que cuentan las tarjetas micro:bit V2. Dado que el enlace Bluetooth posee una unidad máxima de transferencia (MTU) limitada, a menudo truncando mensajes cercanos a los 20 caracteres, se implementó un mecanismo de fragmentación (\emph{chunking}). Los mensajes se estructuran como líneas de texto terminadas en salto de línea, manteniendo una longitud controlada para evitar pérdidas de datos.

Los subflujos creados en el editor visual se compilan a un formato binario personalizado denominado DFBC1 (\emph{Dataflow Byte Code 1.0}). Este formato incluye un encabezado con metadatos y una sección de instrucciones basada en una máquina de pila LIFO (\emph{Last-In, First-Out}). El motor en el micro:bit procesa comandos específicos (como ADD, CONCAT, RETURN) que consumen operandos de la pila, ejecutan la operación y devuelven el resultado.

El proceso de comunicación se divide en fases de transmisión de metadatos (BEGIN), envío del bytecode fragmentado (CHUNK) y confirmación del programa (COMMIT). Una vez el programa reside totalmente en la memoria del micro:bit, el orquestador envía un comando de ejecución (RUN) con los argumentos necesarios, recibiendo posteriormente los resultados o eventos de vuelta en el navegador a través del canal de comunicación establecido (Serial o Bluetooth).

\usubsubsection{Implementación del servidor orquestador}

Para la distribución de tareas entre múltiples computadoras (PCs), se desarrolló una arquitectura cliente-servidor basada en WebSockets. Esta tecnología fue seleccionada por su capacidad de mantener canales bidireccionales persistentes y de baja latencia, esenciales para la sincronización de un flujo de datos en tiempo real.

Se implementó un servidor central que actúa como el orquestador del sistema. Su responsabilidad principal es gestionar el ciclo de vida del grafo de ejecución global. Cuando el usuario inicia el programa, el orquestador analiza el flujo y determina qué nodos deben ejecutarse localmente y cuáles deben delegarse a otros dispositivos conectados (conocidos como \emph{workers}).

El servidor mantiene una tabla de estado de las conexiones. Al recibir un resultado parcial de una PC remota o un micro:bit, el orquestador actualiza las dependencias de los nodos subsiguientes y, si se cumplen las condiciones de disparo (principalmente, disponibilidad de los datos de entrada), envía inmediatamente las nuevas instrucciones a los dispositivos correspondientes. Este diseño centralizado simplifica la gestión de la concurrencia y asegura que los datos fluyan correctamente entre dispositivos heterogéneos.

Este diseño permitió validar la capacidad del sistema para ejecutar algoritmos distribuidos, donde diferentes partes del procesamiento ocurren en distintos dispositivos pero coordinados de manera transparente para el usuario final.

\usubsubsection{Ampliación del catálogo de nodos}

Para soportar estas nuevas capacidades distribuidas, se incorporaron nuevos nodos al lenguaje visual, permitiendo al usuario interactuar explícitamente con las entradas y salidas del sistema distribuido:

\begin{itemize}
    \item \textbf{Interacción con usuario:} Se añadieron los nodos de Entrada (solicitud de datos por teclado) y Opción Aleatoria, para permitir la generación de datos desde el entorno local.
    \item \textbf{Control de Micro:bit:} Se implementaron nodos específicos para interacciones puntuales con las tarjetas micro:bit, tales como Leer botón, Escribir en matriz LED y Emitir Sonido, permitiendo la interacción directa con el hardware.
    \item \textbf{Lógica de control:} Se introdujo el nodo Condicional + Selector, el cual evalúa condiciones lógicas y dirige el flujo de datos hacia diferentes salidas, permitiendo bifurcaciones en la lógica distribuida. Este nodo representa una evolución sobre el planteamiento original de la lógica condicional en el lenguaje, que se basaba en el enrutamiento de datos a través de una condición (Switch). Este enfoque permite una mayor flexibilidad e independencia entre los datos usados en las condiciones, y los datos de salida para cada caso.
    \item \textbf{Editor de fórmulas:} Con el objetivo de optimizar la construcción de expresiones complejas, se implementó un nodo especializado que permite al usuario redactar fórmulas matemáticas mediante una sintaxis textual simplificada, en lugar de una interconexión extensiva de nodos aritméticos básicos. Este componente actúa como un evaluador de expresiones en tiempo de ejecución, procesando múltiples variables de entrada provenientes de otros nodos y consolidando el cálculo en una única salida. Esta adición facilita la transición de los jóvenes hacia formas de pensamiento más abstractas y simbólicas.
\end{itemize}

\usubsubsection{Soporte para recursividad}

Un avance fundamental de este incremento fue la implementación de la recursividad en el paradigma de flujos de datos. Visualmente, esto se resolvió mediante el nodo de abstracción de subflujos: el estudiante puede instanciar este nodo dentro de su propio lienzo interno, haciendo explícita la autorreferencia y asumiendo la responsabilidad de construir un caso base lógico.

Para evitar bucles infinitos y garantizar la estabilidad del sistema, el control se estructuró en dos fases arquitectónicas. Durante la compilación, el motor utiliza un contexto global para rastrear las plantillas activas; al detectar una llamada recursiva, reutiliza la definición ya registrada en lugar de repetir el análisis, evitando ciclos de resolución infinitos. Por otro lado, en tiempo de ejecución, se gestiona un contexto dinámico que actúa como una pila de llamadas controlada. Cada invocación genera una instancia de ejecución independiente para aislar los datos y aumenta un contador de profundidad. Si el caso base del estudiante falla y se alcanza el límite máximo de seguridad preestablecido, el sistema intercepta el flujo y detiene la ejecución con una excepción. Esta arquitectura garantiza un equilibrio óptimo entre la libertad algorítmica del usuario y la protección del entorno en el navegador.

\usubsubsection{Resultados del incremento}

Como resultado de esta iteración, se obtuvo un entorno capaz de ejecutar algoritmos distribuidos donde una parte del procesamiento ocurre en el navegador, otra en dispositivos micro:bit (controlando sensores y actuadores) y otra en PCs remotas, todo coordinado transparentemente por un servidor orquestador. Esta arquitectura validó la viabilidad de la propuesta para soportar sistemas distribuidos de manera accesible para niños y jóvenes, permitiendo la creación de proyectos que integren tanto software como hardware de forma fluida.

No obstante, la evaluación crítica de estos resultados a través de la construcción de casos de prueba arrojó dos hallazgos significativos que evidenciaron oportunidades de mejora frente a los objetivos pedagógicos y funcionales del proyecto.

Primero, aunque la infraestructura base soportaba la comunicación y ejecución distribuida, el lenguaje visual carecía de primitivas que facilitaran aun más la orquestación intuitiva de estas tareas sobre conjuntos de datos (listas). Se identificó la necesidad y la viabilidad de implementar herramientas más concretas, con un mayor nivel de abstracción, para el diseño de algoritmos distribuidos. Específicamente, se planteó, para siguientes incrementos, la adopción de constructos inspirados en las operaciones colectivas de MPI, tales como \textit{scatter} y \textit{gather}, para simplificar visualmente los patrones de división de carga y recolección de resultados.

Por último, se observó que el esquema de integración de las tarjetas micro:bit estaba restringido, relegando a estos dispositivos a un rol pasivo como dispositivos de procesamiento sobre datos enviados desde el programa principal. Esta limitación reducía sustancialmente la utilidad práctica del lenguaje para modelar aplicaciones auténticas orientadas, por ejemplo, al Internet de las Cosas (IoT), donde es fundamental la lectura dinámica de sensores. Por ello, se planteó la necesidad de implementar, en futuros incrementos, un modelo de integración más flexible que permita a los micro:bits actuar como fuentes de datos activas, capaces de emitir eventos al programa principal en respuesta a cambios en sus sensores, habilitando así la creación de proyectos interactivos y reactivos que integren hardware y software de manera fluida.

\usubsection{Tercer incremento}

El objetivo central de este tercer incremento fue la conceptualización e implementación del módulo de “Desafíos”. Tras consolidar un motor de ejecución y un editor funcional en las etapas previas, se abordó la necesidad de dotar a la herramienta de una estructura de apoyo que permitiera a los usuarios familiarizarse con el paradigma de flujos de datos, y con el uso general de la herramienta. Por ello, este módulo se diseñó para funcionar como un sistema de tutoriales gamificados.

\usubsubsection{Refinamiento de la interfaz de usuario del editor}
Para garantizar una experiencia de usuario fluida y minimizar la carga cognitiva, se rediseñó la interfaz del editor principal, transitando de un prototipo funcional a un entorno visualmente pulido y estructurado. Las mejoras implementadas se centraron en la jerarquización de la información, la maximización del espacio de trabajo y el uso de la psicología del color para guiar la interacción. Los cambios más relevantes incluyen:

\begin{itemize}
    \item \textbf{Estructuración de la cabecera (header):} Se incorporó una barra superior persistente de color azul que dota de identidad visual al lenguaje (logo y nombre). En este espacio se reubicaron las acciones globales del sistema, como la carga y descarga de programas y la conexión de dispositivos, separándolas lógicamente del área de construcción de algoritmos.
    \item \textbf{Jerarquización de los controles de ejecución:} Los botones de “Ejecutar” y “Detener” pasaron de ser texto plano a ser elementos prominentes con colores semánticos universales (verde para inicio y rojo para detener). Esto proporciona \textit{affordance} visual, permitiendo a los usuarios identificar instintivamente las acciones de control del programa sin la necesidad estricta de leer.
    \item \textbf{Optimización de la paleta de nodos:} Se redujo el tamaño general de la barra lateral izquierda para ceder mayor espacio en pantalla al lienzo de trabajo. Para mantener la accesibilidad, se integró una nueva columna de navegación rápida con iconos categorizados (Entradas, Proceso, Control, etc.) que coinciden cromáticamente con los nodos, facilitando la búsqueda visual.
    \item \textbf{Compactación de los componentes visuales:} La geometría de los nodos fue rediseñada para ser de menor longitud cuando sea posible. Al ocupar menos espacio individual, se permite que programas con un mayor número de nodos e interconexiones sean visibles simultáneamente en pantalla, reduciendo la necesidad de desplazamiento y facilitando la comprensión de la arquitectura general del flujo de datos.
    \item \textbf{Delimitación del área de salida (consola):} Se aplicó un borde y un fondo de color a la consola de resultados, contrastándola con la cuadrícula del lienzo. Esta separación visual clara ayuda al estudiante a distinguir rápidamente entre el área de construcción lógica y el área de resultados.
\end{itemize}

\usubsubsection{Diseño del módulo de desafíos}

El diseño de este módulo se fundamentó en principios de gamificación y psicología cognitiva. De acuerdo con \citeA{sandhu2013}, la gamificación consiste en utilizar el pensamiento y las dinámicas de los juegos para involucrar a las audiencias en la resolución de problemas. En el contexto del diseño de interfaces para niños, la inclusión de elementos gamificados basados en el aprendizaje resulta fundamental para fomentar la comprensión de conceptos abstractos. Bajo esta premisa, el módulo de desafíos se estructuró para proporcionar una ruta de aprendizaje interactiva e incremental.

Para asegurar la efectividad de los retos, los usuarios se clasificaron según los grupos definidos por Piaget en su teoría del desarrollo cognitivo. El grupo de 8 a 11 años, ubicado en la etapa de Operaciones Concretas, comprende la causalidad pero presenta dificultades ante conceptos puramente abstractos. Por tanto, sus desafíos emplean metáforas visuales manipulables donde la relación entrada-salida es fácilmente observable. En contraste, los jóvenes de 12 a 16 años, en la etapa de Operaciones Formales, poseen un razonamiento abstracto e hipotético-deductivo. En consecuencia, sus retos prescinden de las metáforas directas para introducir lógica compleja y estructuras de datos abstractas, requiriendo planificación algorítmica y manejo concurrente de variables.

Adicionalmente, para evitar la sobrecarga cognitiva en ambos grupos, el módulo implementa el principio de andamiaje. A diferencia del modo de creación libre, el entorno restringe dinámicamente la paleta de herramientas, exponiendo únicamente los nodos necesarios para resolver el nivel en curso. Para complementar esto, se desarrolló un motor de validación automática que evalúa en tiempo real el flujo construido, comparando la salida final generada con el resultado esperado del reto. Esta validación emite un veredicto inmediato de éxito o fallo, fomentando el aprendizaje autónomo basado en el ensayo y error.

\usubsubsection{Formulación de los desafíos}

Para sistematizar la creación de estos retos interactivos y garantizar que cada uno cumpla rigurosamente con los principios de andamiaje y adaptación cognitiva previamente descritos, se diseñó un instrumento estandarizado. Este formato actúa como una plantilla de diseño instruccional que define los parámetros técnicos y narrativos de cada desafío antes de su implementación en el software. Los campos de este formato se detallan en la tabla \ref{tab:formato-desafios}.

Utilizando este formato estandarizado como guía, se diseñó un currículo inicial compuesto por 18 desafíos. Estos se distribuyeron equitativamente, destinando 9 retos para el grupo de niños y 9 para el grupo de jóvenes. Cada conjunto de desafíos fue estructurado para abarcar progresivamente los conceptos fundamentales del lenguaje, comenzando desde la simple interconexión de nodos de lectura y escritura, hasta llegar a la resolución de problemas lógicos y la manipulación concurrente de datos. Esta distribución garantiza una curva de aprendizaje secuencial, asegurando que cada nuevo reto se construya sobre los conocimientos consolidados en el nivel anterior.

\usubsubsection{Diseño de la interfaz de usuario del módulo de desafíos}

Para materializar el módulo de desafíos, el primer paso consistió en reestructurar la arquitectura de la información del sistema. Originalmente, la aplicación constaba de una única vista centralizada en el editor de código. Para integrar la nueva funcionalidad, se implementó un sistema de enrutamiento web a partir de una página de inicio que bifurca la experiencia del usuario, permitiéndole elegir entre el modo de creación libre (editor base) y la ruta de aprendizaje guiada (desafíos).

Al ingresar al módulo de aprendizaje, el flujo de interacción inicia con una pantalla donde el usuario debe seleccionar su rango de edad. Esta interfaz conecta directamente con la estructuración cognitiva definida previamente, y permite al sistema cargar dinámicamente el currículo de retos correspondiente a la etapa de desarrollo del estudiante. En la figura \ref{fig:seleccion-edad} se ilustra esta pantalla de selección de perfil.

Cada parada en este recorrido actúa como un nivel bloqueado o desbloqueado, acompañado de una imagen gráfica representativa de la temática del reto.

Esta disposición espacial y lúdica ofrece al estudiante un sentido claro de progresión y meta. Al interactuar con cada nodo del mapa, el usuario puede visualizar la descripción y los objetivos específicos del desafío, contando con un botón de acción directa para transicionar hacia la pantalla de resolución del nivel seleccionado.

Al seleccionar un nivel específico desde el mapa interactivo, el estudiante ingresa a la pantalla de resolución del desafío, la cual se ilustra en la figura \ref{fig:editor-desafio}. En esta vista, el concepto de andamiaje cognitivo se hace presente, dado que la paleta de nodos en el panel izquierdo se restringe automáticamente para mostrar únicamente los componentes habilitados para esa misión en particular. Por su parte, el lienzo central se inicializa según el escenario definido, pudiendo presentarse completamente en blanco o desplegar una configuración de nodos iniciales preestablecida, estableciendo así el punto de partida lógico para el estudiante.

Para optimizar el uso del espacio y mantener el enfoque visual en el flujo de datos, el panel de información del reto se diseñó como una tarjeta flotante ubicada en la esquina superior derecha del lienzo. Este panel contiene el estado de la misión, el enunciado con las instrucciones redactadas en lenguaje natural y el botón de acción principal para probar la solución construida.

El proceso de validación de desafíos se diseñó para ser transparente y formativo. Al accionar el botón “Probar”, el motor de ejecución orquesta una corrida interna utilizando los casos de prueba definidos en la configuración del nivel. El sistema evalúa el grafo construido por el usuario y contrasta su comportamiento con la salida esperada para cada uno de los casos. Si el flujo lógico es incorrecto, el entorno expone el resultado erróneo obtenido. Esta retroalimentación visual directa permite al estudiante verificar la discrepancia, reflexionar sobre su lógica y aplicar técnicas de depuración basadas en el ensayo y error.

Por el contrario, si la validación es exitosa y el flujo produce el resultado correcto, el sistema activa un refuerzo positivo. Gráficamente, se aprueba la misión y se presenta la opción de avanzar al siguiente nivel, mientras que a nivel auditivo se reproduce un efecto de sonido de recompensa. Este diseño sonoro actúa como un mecanismo de retroalimentación que, en el contexto de la gamificación, incrementa la satisfacción del usuario y fomenta la motivación continua a lo largo de la ruta de aprendizaje.

\usubsubsection{Ampliación del modelo de distribución}

Como parte de las mejoras introducidas en el tercer incremento, se realizó un refinamiento sobre el modelo de ejecución distribuida implementado en la iteración anterior. Para potenciar la capacidad de los estudiantes de abordar problemas basados en el procesamiento paralelo de datos, se incorporaron nuevos componentes al lenguaje visual tomando como inspiración las operaciones definidas en el estándar de Message Passing Interface (MPI). Adaptando este subconjunto de operaciones colectivas se diseñaron e implementaron los siguientes nodos:

\begin{itemize}
    \item \textbf{Distribuir (Scatter):} Este componente se fundamenta en la operación Scatter de MPI, en la cual un proceso distribuye partes de un arreglo de datos a diferentes procesos. En el contexto del lenguaje, este nodo actúa sobre una estructura de datos tipo lista. Al activarse, fragmenta la colección y enruta sus elementos de manera equitativa hacia los distintos dispositivos o nodos de procesamiento conectados.
    \item \textbf{Reunir (Gather):} Su diseño se basa en la operación Gather de MPI, conceptualizada para que varios procesos envíen partes de un arreglo de datos a un proceso central que las recopila. En el entorno desarrollado, este nodo cumple una función de sincronización; espera a que los múltiples nodos distribuidos concluyan su procesamiento y recolecta los resultados individuales, empaquetándolos nuevamente en una única lista de salida para continuar con el flujo lógico del programa principal.
\end{itemize}

La inclusión de estos nodos de distribución y recolección abstrae la complejidad técnica del manejo de múltiples procesos y el paso explícito de mensajes. De esta manera, se permite a los jóvenes modelar e interactuar con conceptos avanzados de paralelismo de datos de forma visual, manteniendo la consistencia del paradigma de flujo de datos y enriqueciendo las capacidades del lenguaje para la programación distribuida.
